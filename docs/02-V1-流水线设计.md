# 02 · V1 流水线设计

## 一、节点清单（24 个）

| 阶段 | 节点 | 作用 |
|---|---|---|
| 触发 | Schedule Trigger | cron `0 20 * * *`，每天 20:00 |
| 抓取 | RSS Feed Read ×4 | IT之家 / 36氪快讯 / 少数派 / 爱范儿 |
| 限流 | Limit ×4 | 每源最多 20 条，控制 token 成本 |
| 归一 | Edit Fields ×4 | 统一成 `标题/摘要/链接/发布时间/媒体` 五个字段，媒体名硬编码区分来源 |
| 合并 | Merge → Merge1 → Merge2 | 两两合并成一条流（n8n 的 Merge 只吃两路输入） |
| 过滤 | Date-Filter | 只留当天发布的 |
| 理解 | Basic LLM Chain + DeepSeek + Structured Output Parser | 判断相关性 + 生成摘要 + 生成「传达信号」 |
| 过滤 | Related-Filter | `output.related === true` |
| 整理 | Edit Fields4 | 映射成入库字段 |
| 存档 | 飞书多维表格 add record | 标题 / 内容 / 传达消息 / 日期(ms) / 媒体 / 链接 |
| 排版 | Code (JavaScript) | 媒体交错取前 10 条，拼飞书卡片 JSON 并推送 |

## 二、日期过滤里的一个坑

最初的写法是 `new Date(发布时间) >= 今天零点`，问题有两个：

1. **手动测试时永远是空的**：白天点执行，当天的新闻还没发全，测试结果看起来像 workflow 坏了
2. **20:00 执行会漏掉前一天晚上的新闻**：20 点跑，只看今天 0 点之后，昨天 21:00~23:59 发的就丢了

最终逻辑：

```js
// 测试模式：取昨天零点之后（方便白天验证）
// 正式执行：取「昨天零点」或「今天零点」，取决于当前是否已过 12 点
new Date(发布时间).getTime() >= Number(
  $execution.mode === 'test'
    ? new Date().setHours(0,0,0,0) - 86400000
    : new Date().setHours(0,0,0,0) - (new Date().getHours() < 12 ? 86400000 : 0)
)
```

**教训**：过滤时间窗要和触发时间一起设计，否则「看起来能跑」的 workflow 每天丢一半新闻。

## 三、提示词设计

```
你是新闻编辑。判断下面这条资讯是否与科技/AI/互联网强相关，并输出：
1. summary：80字以内的中文核心摘要（说清发生了什么）；
2. message：这条新闻背后想传达的核心信息/趋势/信号，50字以内（说清意味着什么）。
资讯：{{ JSON.stringify($json) }}
只输出 JSON。
```

配套 Structured Output Parser 的 schema：

```json
{ "related": true, "summary": "60字以内的中文摘要", "message": "该新闻背后想传达的核心信息或趋势，30字以内" }
```

三个设计点：

- **先判断再生成**：`related` 放在第一个字段，模型必须先在内部做「相关/不相关」的判断，再写摘要，避免对无关新闻也硬写一段
- **两个字段职责分离**：`summary` 回答「发生了什么」，`message` 回答「意味着什么」。这是资讯产品与新闻标题的差别
- **只输出 JSON**：靠 Parser 兜住格式，不写「请用 JSON 格式输出」这种软约束

## 四、媒体交错排版（本版最像「产品」的一段）

直接 `slice(0, 10)` 的后果：36氪快讯更新最快，前 10 条可能 8 条来自它，其它三家一条不剩，用户感知是「这个产品只有一个源」。

Code 节点的做法：

```js
// 按媒体分组
const groups = {};
for (const it of items) (groups[it.json.媒体] ||= []).push(it);

// 轮询取：IT之家1条 → 36氪1条 → 少数派1条 → 爱范儿1条 → 循环
const interleaved = [];
let added = true;
while (added) {
  added = false;
  for (const m of Object.keys(groups)) {
    if (groups[m].length) { interleaved.push(groups[m].shift()); added = true; }
  }
}
const selected = interleaved.slice(0, 10);
```

效果：前 10 条里四家媒体都能露出，且**更新快的源仍然占更多席位**（因为它的池子更深），不是平均分配——这是刻意的：既要多样性，也要时效性。

## 五、飞书卡片结构

- header：`📰 每日科技新闻速递`，副标题列出四个源
- 第一行：`今日共 N 条科技资讯 · 日期`（N 是过滤后的总数，不是推送的 10 条）
- 每条：序号+标题加粗 / 摘要 / `📣 传达：xxx` / `🗞 媒体 · 🕒 时间 · [原文](链接)`
- 每条之间用 div 分隔，卡片 `wide_screen_mode`，支持转发

## 六、已知问题

- 同一新闻被多源转载会重复（V2 用查重解决）
- 相关性判断偶有误杀（把「某公司财报」判成不相关），目前靠人工回看多维表格发现
- 卡片生成失败时整条推送失败，没有降级到纯文本
