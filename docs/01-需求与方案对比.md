# 01 · 需求与方案对比

## 一、需求从哪来

自己做 AI 方向，每天要看 4 个科技媒体的 AI 相关新闻：IT之家（快）、36氪（商业视角）、少数派（产品视角）、爱范儿（消费电子）。三个问题：

1. **信息过载**：4 个源一天几百条，真正与 AI 相关的不到 10 条，人工筛要 20 分钟
2. **只看标题没有判断**：知道「某公司发布模型」，但不知道「这意味着什么」
3. **散落各处**：看完就忘，没有沉淀，想回查找不到

需求因此拆成五步：**抓取 → 过滤 → 理解 → 触达 → 存档**。

## 二、需求拆解与方案映射

| 环节 | 需求 | V1 实现 | V2 实现 |
|---|---|---|---|
| 抓取 | 多源、当天 | 4 个 RSS 节点并行，各限 20 条 | 1 个聚合 API 工具，模型按需调用 |
| 过滤 | 只留 AI/科技相关 | LLM 判断 + 结构化布尔值硬过滤 | 模型在 SOP 内自主挑 3~5 条 |
| 理解 | 发生了什么 + 意味着什么 | 摘要 80 字 + 传达信号 50 字 | 摘要 80 字 + 一句解读 |
| 触达 | 一屏看完 | 飞书卡片，按媒体交错取前 10 | 飞书卡片 Markdown + 日程提醒 |
| 存档 | 可回查 | 写入飞书多维表格 | 同左，且用于查重 |

## 三、两种技术路线的取舍

### V1 确定性流水线

- **优势**：每一步可单独测试；第 3 条新闻为什么被过滤掉，能点开节点看到模型的原始返回；成本可预估（固定 4×20 条调用）
- **劣势**：编排重。加一个数据源要新增 3 个节点再改合并链路；跨源去重、跨系统取数（日程）这类「需要临场判断」的事做不了

### V2 Agentic 编排

- **优势**：加数据源只需加一个工具；「先查重再写库」这种带前置条件的流程，用自然语言 SOP 描述比画 5 个连线更快；可以顺手把日程提醒塞进同一条卡片
- **劣势**：不可控。模型可能漏掉某一步、把 JSON 结构写错、或者多调一次接口；单次成本更高；排障要看 Agent 的思考过程而不是节点输出

## 四、结论：不是替代，是分工

**规则明确、要求稳定的部分留在流水线里；需要临场判断、组合多系统的部分交给 Agent。**

所以最终形态是两套并存：V1 适合「我要每天准点收到、不能漏、成本要可控」，V2 适合「我想快速试新数据源、想让它顺手把别的事也做了」。真正上生产时，我的选择是**用 V1 保底、用 V2 做增量**——这也是我在面试里会讲的判断。

## 五、没做的部分

- 没有做用户调研：这是自用工具，需求来自自己的使用痛点
- 没有做多用户：飞书凭证是单租户的
- 没有评估摘要质量：目前靠人工看卡片判断「这条摘要写得像不像人话」
