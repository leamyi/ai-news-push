# 03 · V2 Agent 设计

## 一、为什么改成 Agent

V1 跑稳之后，我真实遇到的三个约束：

1. **加源成本高**：想多看一个「机器之心」，要新增 RSS 节点 + Limit + Edit Fields，再改两层 Merge 连线
2. **跨源重复**：同一条 OpenAI 新闻在 4 个源都出现，卡片里出现 3 次
3. **想加日程提醒**：需要再开一条支线去查飞书日历，然后合并两个分支的输出

这三件事的共同点是：**它们都不是固定流程，而是「看情况决定」**。这恰好是 Agent 的适用场景。

## 二、架构：一个 Agent + 四个工具

| 工具 | 类型 | 参数/作用 |
|---|---|---|
| 多维表格搜索 | 飞书节点（ai_tool） | 按「创建时间 = 今天/昨天」查已有记录，用于查重 |
| HTTP 请求（60s 早报） | HTTP Request Tool | GET `https://60s.viki.moe/v2/60s`，拿当日 10 条要闻 |
| 多维表格新增记录 | 飞书节点（ai_tool） | 写入标题/链接/摘要/日期/媒体 |
| 飞书日历查询 | 飞书节点（ai_tool） | `calendar:listEvents`，今天零点 → 7 天后，拿未来 7 天日程 |

输出：Agent 生成 Markdown → HTTP 节点用飞书机器人 Webhook 发交互卡片。

注意 V2 **没有做「LLM 生成卡片 JSON」**，而是让 Agent 输出 Markdown，卡片外壳由固定 JSON 包住。理由：卡片结构一旦交给模型，格式错误的概率远高于收益。

## 三、SOP 提示词（核心资产）

```text
你是一个每日新闻推送助手，当前时间是 {{ $now.format("yyyy-MM-dd HH:mm", "Asia/Shanghai") }}。严格按以下步骤执行：

【第一步：查重】
使用「多维表格搜索」工具，查询表中「日期」为 Today 的已有记录，记住已有标题，避免重复。

【第二步：获取新闻】
使用 HTTP 请求工具访问 https://60s.viki.moe/v2/60s，从返回的 data.news 数组（当日10条要闻）中
挑出 3~5 条与科技/AI/互联网最相关的。每条整理为：
- 标题 = 原文
- 发布日期 = 今天
- 发布媒体 = "每日60秒早报"
- 核心摘要 = 你对该条的一两句解读（80字内）
- 链接 = 使用 HTTP 工具返回的 JSON 中 data.link 字段的值

【第三步：写入表格】
使用「新增记录」工具，请求体 JSON 必须严格使用以下格式（每条新闻调用一次）：
{"fields":{"新闻标题":"标题","链接":{"text":"点击查看详情","link":"https://..."},
"内容":"核心摘要","日期":<毫秒时间戳>,"媒体":"每日60秒早报"}}
注意：链接字段的值是对象（text+link 两个键）；日期是毫秒级时间戳数字，不是字符串。

【第四步：查日程】
使用「日历查询」工具（日历 ID: primary，开始时间=今天零点，结束时间=7天后），获取我未来 7 天的日程。

【输出】
输出一段 Markdown（卡片消息用），格式如下，每条新闻间空一行：…
最后加一段「📅 日程提醒」：列出未来7天日程；无日程则写"今日无日程安排"。
只输出这段 Markdown 本身，不要输出其他解释。
```

## 四、三个踩坑与修法

### 坑 1：链接字段类型错

第一版没给示例，模型把链接写成 `"链接": "https://..."` 字符串，而飞书多维表格的超链接字段要求 `{text, link}` 对象，写入全部失败。

**修法**：在 SOP 里直接给完整请求体示例，并用一句话点明「链接字段的值是对象」。「给结构示例」比「描述字段类型」有效得多。

### 坑 2：日期写成 `"2026-11-01"`

飞书日期字段要毫秒时间戳。模型很自然写成年月日字符串。

**修法**：示例里写 `<毫秒时间戳>`，并补一句「日期是毫秒级时间戳数字，不是字符串」。

### 坑 3：模型不查重、直接写库

步骤写着「查重」，但模型有时跳过第一步。表现是同一批新闻重复入库。

**修法**：把查重从「建议」变成流程的**前置步骤**，并在第一步显式说明「记住已有标题，避免重复」——给模型一个明确的中间产物（列表），它才会真的去比对。

## 五、成本与可控性

| | V1 | V2 |
|---|---|---|
| 单次 LLM 调用 | 4×20 条各一次（批处理） | 1 次 Agent 多轮（含工具调用） |
| token 消耗 | 高（每条都要摘要） | 中（只处理 3~5 条） |
| 出错影响面 | 单条失败 | 整轮失败 |
| 排障方式 | 看节点输出 | 看 Agent 思考轨迹 + 工具调用记录 |

V2 的实际体验是：**成本更低、灵活性更高，但「今天没收到推送」的排查时间更长**。所以生产上我会让 V1 兜底。

## 六、可复用的设计原则

1. **工具给能力，SOP 给顺序**：不要把流程写进代码，也不要让模型自己发明流程
2. **强结构的地方给死示例**：请求体、字段类型、时间格式，一律贴样例
3. **让模型产出中间可见物**：如「已有标题列表」，否则它不会真的执行查重
4. **卡片外壳不进模型**：模型只产出内容（Markdown），结构由代码固定

这套原则后来被我复用到了另一个项目（考研每日一站的推送卡片）上。
